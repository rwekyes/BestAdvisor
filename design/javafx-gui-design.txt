================================================================================
BetterAdvisor — JavaFX GUI Design Specification
================================================================================
This document describes the screen layout, component choices, and wiring
for every major view in the application. JavaFX class names are used
throughout (e.g., TreeView, TableView, BorderPane).

Naming convention used below:
  [FX:ClassName]  = the JavaFX control or layout to use
  [SCENE]         = a top-level scene (one per major screen)
  [FXML]          = the corresponding FXML file path (relative to src/)

--------------------------------------------------------------------------------
SECTION 1 — APPLICATION SHELL
--------------------------------------------------------------------------------

The application uses a single-window, single-stage model. Every scene is
loaded into the primary Stage via a SceneManager singleton (State Pattern).

Primary Stage properties:
  Title:   "BetterAdvisor"
  Size:    1280 × 800 (minimum), resizable
  Style:   StageStyle.DECORATED

Root layout for authenticated screens:
  [FX:BorderPane]
    LEFT   → NavigationPanel (see Section 3)
    TOP    → TopBar (see Section 2)
    CENTER → ContentArea — swapped by SceneManager
    BOTTOM → StatusBar [FX:HBox] showing current user, session time, messages

    Student factory  → StudentNavMenuFactory  (US-AF03)
    Faculty factory  → FacultyNavMenuFactory  (US-AF04)
    Admin factory    → AdminNavMenuFactory     (US-AF05)

  Each NavItem cell:
    [FX:HBox] → [FX:ImageView] icon + [FX:Label] itemName

    NavMenuFactory.create(role) which returns the correct List<NavItem>.
    The list is set on the ListView's ObservableList.

SECTION 7 — SCHEDULE OF CLASSES / CATALOG (Composite Pattern)
--------------------------------------------------------------------------------

[SCENE] CatalogScene
[FXML]  views/CatalogView.fxml

[FX:BorderPane]
  TOP:
    [FX:HBox]
      [FX:TextField] searchField (prompt: "Search by code or keyword")
      [FX:Button]    "Search"    → calls CatalogSearchCommand (US-C02)
      [FX:Button]    "Clear"     → resets tree to full catalog

  CENTER:
    [FX:SplitPane] (horizontal)
      LEFT (60%):
        [FX:TreeView<CatalogNode>] catalogTree
          Root: hidden root
          Level 1: CollegeNode   (shows: name, dept count, section count, credits)
          Level 2: DepartmentNode
          Level 3: CourseNode    (shows: code, name, credits)
          Level 4: SectionNode   (leaf — shows: section #, instructor, seats)

          CellFactory renders each level with a different icon.
          Expanding a node loads children lazily (TreeItem.expanded listener).
          Credit/section roll-up is computed in CompositeNode.getCredits()
          and displayed in the cell.

      RIGHT (40%):
        [FX:ScrollPane] containing SectionDetailPanel (US-C06)
          Populated when a SectionNode leaf is selected in the tree.

          [FX:VBox]
            [FX:Label]  "Section Detail"
            [FX:GridPane] (label-value pairs):
              Instructor | <name>
              Days       | MWF
              Time       | 10:00 AM – 10:50 AM
              Room       | Bldg 4, Room 201
              Seats      | 30 total / 22 enrolled / 3 waitlisted
              Delivery   | In-Person
            [FX:Button] "Add to Cart" → PreRegistrationCommand

Search behavior (US-C02):
  CatalogSearchCommand walks the entire composite tree using a post-order
  iterator, collects matching SectionNodes, and rebuilds a filtered
  TreeView showing only the path College→Dept→Course→Section for each match.

SECTION 17 — REGISTRATION PIPELINE UI (Chain of Responsibility)
--------------------------------------------------------------------------------

Registration is not a separate full scene — it is triggered from
CatalogScene or SectionSearchScene and runs as a modal flow.

Flow:
  1. Student clicks "Add to Cart" / "Add Selected Section".
  2. RegistrationCommand is constructed and passed to the chain head.
  3. Each handler in the chain either:
       a. Passes to the next handler (silently), or
       b. Throws a RegistrationHandlerException with a message string.
  4. If an exception is thrown:
       [FX:Alert] AlertType.ERROR
         Header:  handler name (e.g., "Prerequisite Check")
         Content: specific message (US-X01)
         Button:  "OK"
  5. Seat Availability check (US-R11):
       If section full: [FX:Alert] AlertType.CONFIRMATION
         "This section is full. Add to waitlist?"
         Buttons: "Yes, Waitlist Me" | "Cancel"
  6. All checks pass:
       [FX:Alert] AlertType.INFORMATION
         "Successfully enrolled in <SectionCode>."
       Dashboard and schedule widgets refresh.

Audit log entry written after every pipeline run (US-X02).

SECTION 23 — SCHEDULE CONFLICT DETECTION (Iterator Pattern)
--------------------------------------------------------------------------------

Conflict detection (US-I16) runs inside the Registration Pipeline
(ScheduleConflictCheck handler) before the UI confirmation is shown.

The algorithm:
  ScheduleConflictIterator simultaneously walks:
    - The student's enrolled sections (ordered by day+time)
    - The proposed section's meeting slots
  If any day-and-time overlap is found, the handler throws
  RegistrationHandlerException("Schedule Conflict") with the message:
    "This section conflicts with <ExistingSection> on <Day> at <Time>."
  Displayed to the user as an [FX:Alert] AlertType.ERROR.
